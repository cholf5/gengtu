# 连续字幕截图生成器设计

日期：2026-06-21

## 1. 产品定位与入口

连续字幕截图生成器定位为“精选模板之外的固定格式工具”，不是用户上传模板系统，也不是通用图片编辑器。网站主定位仍然是“精选模板，一键成梗”；新功能只补充一种常见梗图格式：上传一张截图或底图，输入多行台词，生成“人物连续说话”的长图。

入口采用 Header 独立入口，文案建议用“连续字幕”或“字幕截图”，进入独立路由，例如 `/caption`。它不进入 Gallery 模板列表，也不作为特殊模板卡片出现，避免污染“作者精选模板”的语义。页面内应明确提示：图片仅在浏览器本地处理，不上传、不保存；这个工具只生成固定结构的连续字幕图。

功能边界上，允许复用 MemeEditor 的文字样式能力，但只作用于“字幕文字”。不支持自由拖拽文本框，不支持新增多个任意文本层，不支持裁剪、贴纸、滤镜、模板保存或公开上传。这样它比极简工具更实用，但仍是“固定结构 + 可调字幕样式”，不会滑向完整图片编辑器。

## 2. 生成规则与视觉结构

生成结果采用“第一句覆盖原图，后续句子追加底部片段”的结构。用户上传一张底图后，输入多行字幕；按换行拆分为多句，忽略首尾空白，空行默认过滤。若有 N 行有效字幕，则输出画布包含：完整底图一份，并在底图底部绘制第 1 行字幕；然后追加 N-1 个字幕块。每个追加字幕块的背景都来自底图最下面的一段区域，每个块上分别绘制第 2 行、第 3 行等字幕。

字幕块高度不由用户手动设置，而是根据当前文字样式自动计算。大致由字号、行高、上下 padding、描边/阴影余量共同决定。然后从底图底部裁出同样高度的背景区域，复制到输出图下方。这样字号越大，每行块越高，视觉上自然；同时不需要额外增加“字幕区域高度”滑块。

背景保持原样，不加黑底、不加遮罩、不做亮化或暗化。字幕可读性由文字样式负责，例如白字黑描边、阴影、glow、颜色和描边宽度。若底图底部原本有字幕或杂乱内容，新字幕会直接覆盖在其上，页面可以给出轻提示，但不提供擦除或去字幕能力。

## 3. 页面交互与状态

`/caption` 页面建议采用左右或上下响应式布局，风格延续现有 Ant Design 卡片和 Inspector。页面主要包含四块：图片选择、字幕输入、预览区域、文字样式设置。上传控件只读取本地图片文件，生成 `objectURL` 或 Data URL 用于预览和 Canvas 绘制；离开页面或替换图片时释放旧资源，避免内存泄漏。

字幕输入使用一个多行文本框，提示“每行一句字幕”。有效字幕行实时派生，预览实时更新。若尚未上传图片，预览区域显示占位说明；若没有有效字幕，则只展示底图或提示输入字幕。下载按钮在图片和至少一行字幕存在时可用。可以沿用现有编辑器里的下载/复制体验，但初版至少保证下载 PNG；复制到剪贴板可以作为同级能力，如果复用成本低就保留，否则后续再加。

样式区域直接复用 `TextStyleInspector`，维护一个全局 `TextStyleSettings`。所有字幕行共享同一套样式，不做逐行不同样式。建议默认样式选择“白字黑描边、居中、底部对齐或中间对齐、较大字号”，贴近字幕梗图默认观感。由于没有自由文本框，`SelectedTextInspector` 不整体复用；更适合复用其中的 `TextStyleInspector`，另写一个轻量的 caption inspector 容器。

## 4. 架构、复用与数据流

路由继续沿用当前手写路由方式，在 `App.tsx` 的 view union 中增加 `caption`，`getViewFromLocation()` 识别 `/caption`，Header 增加独立按钮。保持 `BASE_URL` 拼接方式，不硬编码根路径。新增组件可以叫 `CaptionGenerator` 或 `CaptionScreenshotGenerator`，放在 `src/components/`。它不接入模板 manifest，也不产生新的模板 JSON。

渲染逻辑建议放在 `src/utils/captionCanvas.ts`，不要堆在组件里。这个工具接收图片源、字幕行、样式和导出缩放，输出 Canvas 或触发下载。为了避免复制 MemeEditor 的文字绘制语义，可以把 `canvas.ts` 里当前私有的 `drawTextField`、必要的 `canvasToBlob`/图片加载能力抽成可复用导出，或者提取到更中性的 `textCanvas.ts`。连续字幕生成时，把每句字幕构造成一个临时 `EditableTextField`，复用同一套文字绘制函数。

数据流上，组件持有：上传图片 URL、自然尺寸、原始字幕文本、派生字幕行、全局文字样式、生成状态和错误消息。预览可用普通 DOM：上方 `<img>` 显示底图，底部追加若干块使用同一张图的底部片段作为背景，再叠加文字。最终导出必须走 Canvas，确保下载结果和预览语义一致。若 DOM 预览和 Canvas 有差异，应以 Canvas 规则为准，并尽量共享计算函数。

## 5. 错误处理、限制与测试

错误处理保持轻量但明确。上传时只接受常见图片类型，例如 PNG、JPEG、WebP；如果图片加载失败，展示 Ant Design `Alert` 或 `message.error`。超大图片可能导致 Canvas 内存压力，建议初版设置一个保守限制，例如自然宽高乘积超过某个阈值时提示用户换小图，或者导出时自动按最大边缩放。图片处理必须完全本地完成，不发请求、不存储、不加入 manifest。

字幕输入可以限制到一个合理范围，例如最多 20 行有效字幕，避免生成极长画布导致浏览器卡顿。空行默认过滤；如果用户只输入空白，下载按钮禁用并提示“请输入至少一行字幕”。如果第一行字幕会覆盖原图底部已有内容，这是预期行为，只做说明，不提供修复工具。

测试方面，建议新增纯函数测试，而不是只做组件手测。可测内容包括：字幕行解析、字幕块高度计算、输出画布尺寸计算、追加块数量规则、过多行限制。Canvas 像素级测试可以不做，避免脆弱；但应运行 `npm run test` 和 `npm run build`。手动验收包括：上传图片、输入多行、调整字号/颜色/effect、确认预览和下载结构一致、切换路由返回首页正常。
